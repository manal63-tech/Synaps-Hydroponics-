## 4. The new 3-level pipeline (`decision.py`)

```
Level 1 — Monitoring / physical validity
    All 8 variables are read. The 5 model variables are checked against
    physical_bounds (metadata.json) -- a failure here is blocking, skips
    Level 2/3 entirely, and returns severity="sensor_fault".
    water_level / outside temp / outside humidity are checked separately
    against context_bounds -- a failure here is reported but never blocks
    anything (matches your dashboard's "Sensor Health is separate from
    plant/environment anomalies").

Level 2 — Isolation Forest
    Runs on exactly the 5 trained variables -> NORMAL / ANOMALY + score.
    water_level is intentionally NOT one of them (never was, in your
    notebook) -- it's handled by a simple rule instead (Level 3).

Level 3 — Agronomic / safety rules (simple, deterministic)
    pH, TDS, water_temp -> compared to safe_ranges -> ok / attention
    water_level          -> compared to water_level_thresholds -> ok / low / critical_low

Combined into one severity (dashboard vocabulary: normal / investigate /
critical / sensor_fault):
    anomaly + out-of-range  -> critical
    anomaly only            -> investigate
    neither                 -> normal
    water_level "low"       -> raises to at least investigate
    water_level "critical"  -> raises to critical, regardless of the model
                               (an empty tank is critical even if nothing
                               else looks statistically unusual)
```

## 5. Design choices made on your behalf (flagging so you can override)

- **Growth-stage-aware thresholds dropped.** The old `decision.py` varied
  TDS safe ranges by `growth_days` (DAP). The new Level 3 uses fixed
  ranges from `metadata.json`, matching what you validated in the report.
  `plantation.py` / `growth_days` are still computed and stored (so
  nothing breaks), just no longer used *inside* the decision itself.
- **No more automatic actuator-command suggestions** (`MANUAL_LOWER_PH`,
  etc.). `actuator_command` still exists as a field (so `db_models.py`
  stays happy) but is now just a short label matching whichever Level-3
  rule fired (`PH`, `TDS`, `WATER_TEMP`, `WATER_LEVEL`, `ANOMALY`, `NONE`)
  — informational, never auto-executed, matching "sans commande aveugle."
- **`plant_health_score` / harvest-day estimation removed.** Not part of
  the 3-level architecture you described. Say the word if you want them
  back as a separate, clearly-optional display feature.
- **water_level thresholds (15% / 30%)** are carried over unchanged from
  your old `safety.py` — adjust in `metadata.json` if they don't match
  your actual reservoir.

## Test results (Flask test client, SQLite, real model from Section 12)

| Case | Input | Result |
|---|---|---|
| Hand-typed "plausible" reading | pH 6.0, TDS 900, 24°C/65%, water 21°C, level 78% | `investigate` — see note below, this is not a bug |
| Impossible humidity (150%) | — | `sensor_fault`, `final_decision="Sensor Fault"` |
| Water level critical (5%) | otherwise normal | `critical`, `water_level_status="critical_low"` |
| pH out of range (8.9) | otherwise normal | `critical`, `ph_status="attention"` |
| Water temp extreme (38°C, single-sensor) | otherwise normal | `critical` (Level 3 rule alone is enough here) |
| pH+TDS combined (joint spike) | pH 8.7, TDS 2400 | `critical`, caught by the model -- matches the report's documented strength (joint_spike, F1≈0.78) |
| Outside humidity impossible (250%) | model sensors fine | Level 2/3 still ran; reported under `level1.context_issues`, did **not** force `sensor_fault` |
| `/api/latest`, `/api/history`, `/api/led` (GET+POST) | — | all respond correctly, DB persistence confirmed |

**Note on the first row:** Isolation Forest judges the *joint* combination
against what it actually saw in training, not whether each value sounds
reasonable on its own. A hand-typed guess isn't guaranteed to land inside
a tightly-clustered real operating envelope. The number that actually
matters is the one already validated in the report: **0.51% flag rate on
real held-out test data (25/4,901)**. For a real sanity check, test with
actual rows from the training CSV or real ESP32 readings, not invented
values.
